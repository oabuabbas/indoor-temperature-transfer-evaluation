## D. Safe validation and full rerun

Run the following from the project root to validate saved outputs **without recomputing holdout predictions**:

```text
python -m unittest discover -p 'test_*.py'
python verify_paper_outputs.py
python build_paper_tables.py
python plot_ideal_holdout.py
```

`verify_paper_outputs.py` checks the two stored protocol hashes, house split membership, per-window model/count consistency, reported home-level MAEs and archive size/modification metadata. It does not independently reconstruct every feature or rerun model training; it does not freshly hash the large raw archive. To rehash that archive against the provider MD5, run `python verify_ideal_archive.py` and inspect `outputs/ideal_archive_verification.json`.

For a full independent rerun, use an isolated copy of the project with the original data files available and **without existing generated caches or holdout output files**, retaining the frozen protocols and exact house assignment. This matters because cached sensor and hourly files can otherwise be reused, and `ideal_holdout_prepare.py`/`ideal_holdout_v1.py` deliberately refuse to overwrite existing holdout outputs. Download original archives with source-provided checksums, perform the metadata and raw quality audits, reconstruct development-source and holdout hourly files, train the source model and run the locked holdout protocol in the stated chronological order. Compare resulting output files and hashes; document software, data versions and any differences. Never silently remove or overwrite the original run to make the rerun work. The official compressed room archive alone needs about 10 GB of storage, and full reprocessing is computationally substantial.

An isolated same-machine rebuild was subsequently completed on 29 October 2026 in `replay_clean_20261029`. It regenerated both raw temperature-range quality audits, the development models, the locked holdout evaluation and the secondary holdout sensitivity with separate output caches, and compared 12 detailed CSV outputs and four summary JSON files with the recorded run (absolute tolerance 1e-8, relative tolerance 1e-9). Nine IDEAL-focused unit tests passed in the replay; `outputs/clean_replay_comparison.json` in that directory records the comparison. The original 10 GB archive and two supporting archives were shared read-only by hardlink, while copied code and protocols were hash-checked. This was not independent replication by another analyst, dataset, machine or software environment, and it did not reproduce all exploratory non-IDEAL experiments. See `تقرير_إعادة_البناء_المعزولة.md` for scope.

No public repository or permanent code archive has been created. Before publication, the author must independently execute or review the pipeline, the role and availability of each predictor, mask and target, physical interpretation and data licences.

## E. Interpretation limitations

The primary contrast compares a past-label-based selector to past-label-based local ridge, not two zero-shot methods. Outcomes were not computed for holdout homes before the local holdout protocol was written, but other-site experiments, metadata, quality summaries and IDEAL development outcomes were examined beforehand. The split is not public preregistration. House-level resampling is a descriptive reweighting of the present region, not a confidence interval for independent sites or a population. The secondary range analysis was designed after the primary holdout result, and can alter aggregated targets. No measurement proves control performance, comfort, or energy savings.

## F. Subsequent Bremen external dataset evaluation

The Office Temperatures Bremen repository (https://github.com/ComNets-Bremen/Office-Temperatures, commit `d83ff1e66d41ac8f77a44d5d94fb877b00b842eb`, stated CC BY 4.0) supplies four office temperature series. Source attribution and licence terms require final author verification. See `protocol_bremen_quality.md`, `audit_bremen.py`, `outputs/bremen_manifest.json`, `outputs/bremen_quality.csv`, `protocol_bremen_fallback_v1.md`, `bremen_fallback_v1.py`, and `outputs/bremen_fallback_v1_summary.json` with accompanying CSVs. The versioned raw files and derived hourly files are hash checked; `python verify_bremen_fallback.py` checks stored aggregation and hashes but does not independently rerun forecasts. The plotting script is `plot_bremen_fallback_v1.py`. This evaluation was not included in the earlier isolated IDEAL rebuild.

The protocol was fixed locally after IDEAL results and Bremen input-quality inspection but before Bremen prediction errors, without public preregistration. Hourly averages are only available at the end of their labelled hour; instantaneous availability at that point is assumed, not measured. The hourly criteria differ from IDEAL. The room series are not independent sites; inference about live uptime, outages, climate generalization, energy or control is unsupported. Compare forecast accuracy only on explicitly matched supports; fallback was used in 135 of 29,136 opportunities.

## G. Post-result synthetic input outage sensitivity

See `protocol_bremen_outage_stress_v1.md`, `bremen_outage_stress_v1.py`, `outputs/bremen_outage_stress_v1_summary.json`, replicate, method, pair, branch, choice and mask metadata CSV files, `verify_bremen_outage_stress.py`, and `test_bremen_outage_stress.py`. A locally specified protocol was fixed after previous results and before this analysis; it is not public preregistration. Masks affect inputs and history including history labels; the original target is retained as a retrospective scoring oracle only. It is not evidence that an independent target would be available during actual sensor failure. Five seeds per synthetic scenario are not independent sites. Readiness and matched-support MAE have distinct denominators. The no-additional-mask run reproduces all six saved method-level Bremen results and monthly choices. Verification checks arithmetic, not independent reconstruction. An initial branch scoring-count bug on abstention was fixed and rerun; affected superseded files are preserved in `outputs/bremen_outage_stress_v1_superseded/`.

## J. 2026 nonlinear comparator in Bolzano

The subsequently specified `protocol_bolzano_2026_benchmark_v1.md` evaluates January–April 2026 after prior 2024–2025 outcomes and raw quality inspection but before 2026 errors were computed. See `bolzano_2026_benchmark_v1.py`, the JSON summary with dependency versions and raw SHA-256, per-issue/monthly/choices files, `verify_bolzano_2026_benchmark_v1.py`, and tests. The 2026 file was excluded from the earlier experiment in Section I, but is used here for test and available past local history. ## K. Post-result Bremen nonlinear comparison

The locally fixed `protocol_bremen_nonlinear_benchmark_v1.md` was written after both earlier Bremen outcomes and the Bolzano nonlinear comparison were known. `bremen_nonlinear_benchmark_v1.py` verifies source files and reconstructs all six earlier methods for each of 40 room-months before fitting the fixed local boosting comparator. The model configuration is the one already used in the Bolzano 2026 benchmark, with three matched inputs and the same history as local ridge; it was not tuned to Bremen errors. Per-issue predictions and room/month/own-support outputs are under `outputs/bremen_nonlinear_benchmark_v1_*`; `verify_bremen_nonlinear_benchmark_v1.py` checks protocol hashes, temporal constraints, routing and saved arithmetic, but does not independently refit models. Metrics are equal-room mean MAE and equal-room mean RMSE on the common support of seven methods, not pooled RMSE; the four correlated rooms are not four independent sites. The comparison is post-result and does not show general superiority over nonlinear methods.

## L. Subsequent IDEAL nonlinear selection and later-period comparison

`protocol_ideal_nonlinear_tuning_v1.md` was locally fixed after prior holdout outcomes. The partial preliminary development process was stopped before candidate outputs were saved or printed so the earlier-development/later-test split could be specified. `ideal_nonlinear_tuning_v1.py` selects from three fixed configurations on development-validation homes in October 2017–January 2018; its choice and artifact hashes are stored before `ideal_nonlinear_holdout_secondary_v1.py` evaluates the selected candidate on the original eligible February–June windows of disjoint holdout homes. The first test month's preceding local history may include January data from its own home. The original primary analysis is unchanged and earlier holdout outcomes were already known; this is not a fresh blinded test. Source, development and holdout homes remain geographically clustered in one region. `verify_ideal_nonlinear_tuning_v1.py` checks stored arithmetic, hashes and temporal split, not independent refitting or point-level reconstruction of the earlier predictions. A small grid and same features do not establish the best possible nonlinear model.

## M. Subsequent external Aalborg building

Melgaard et al. dataset v3 (https://doi.org/10.5281/zenodo.10673763, CC BY 4.0) describes six office rooms in one building. File `dataset__2023_02_27__2023_12_31.csv` is checked against published MD5 and local SHA-256. Room data were timestamp-aligned by the data authors; outdoor temperature was interpolated upstream and was not used. UTC offset conversion precedes five-minute and hourly aggregation. See `protocol_aalborg_external_v1.md`, `aalborg_external_v1.py`, `outputs/aalborg_external_v1_summary.json`, room/month/choice/own-support and per-issue files, and `verify_aalborg_external_v1.py`. The protocol was locally fixed after source-quality checks but before Aalborg forecast errors, and after earlier study outcomes; no public preregistration or independent analyst review. The IDEAL source and development-selected boosting settings were fixed before Aalborg evaluation, while locally trained methods and selector require prior target-room labels. The support of all eight predictions plus observed target was used for equal-room MAE and mean room RMSE. The branch fallback was never invoked; uptime, control and population conclusions are unsupported. Verification does not refit source or local models.
