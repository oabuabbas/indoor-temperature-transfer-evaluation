# Post-result exploratory availability audit for IDEAL holdout

Designed after inspecting holdout results and their exclusions; not a new independent test, not real-time deployment validation and does not modify the primary outcomes. Reuse the 73 selected holdout sensors, their saved hourly 10–45°C observations and original nine monthly windows from `protocol_ideal_holdout_v1.md`. Forecast horizon is six hours; timestamps are starts of hourly bins and inputs only become available after the corresponding hour ends. No simulation, interpolation or assumption about communication delay.

Define an issue opportunity as each hourly bin start t in a prescribed calendar window with t>=window start and t+6h<window end. Report two denominators: all such opportunities across the 73 homes, including periods before installation or after recording, and the retrospective recorded span, where floor(first raw timestamp) <= t <= floor(last raw timestamp) according to the original raw-sensor quality audit. The latter is a descriptive study-period bound derived from both ends of the full record, not a decision available at installation, and can contain gaps. Do not label the all-calendar denominator as sensor uptime or the bounded denominator as live uptime.

For each opportunity, report availability using inputs only: persistence requires temp[t]; daily reference requires temp[t-18h]; the source ridge requires temp[t], temp[t-1h] and temp[t-18h]; the selector and local ridge additionally require at least 24 eligible history rows from the preceding 30-day window whose target-hour start precedes the current monthly boundary, fixed once at the boundary. The history uses actual prior target values, never the future target. The selector and local ridge share the same input/history eligibility but may have different computation or communication costs, which are not measured. The chosen selector candidate is not used to relax missing-feature requirements: original code evaluates all candidates on common feature rows.

Separately report retrospective evaluability, not operational availability: selector/local input eligibility plus presence of the eventual target hourly mean at t+6. Reconstruct the 657 home-months and verify original history/test counts and exact inclusion/exclusion decisions against primary holdout output. Sum `primary_scored_rows` only for windows that meet the original retrospective >=24 test-row rule, and require exactly 239215 scored opportunities and 477 eligible windows. This test-row rule uses outcomes later and therefore must not be used to estimate issue-time availability. Count and clearly report the remaining scoreable rows in windows excluded by the primary rule.

Aggregate counts across homes and windows and also report per-home median and range for the within-span fraction, with denominator weighting explicit. This analysis concerns the observed historical record, clustered region, and imposed preprocessing. It does not establish real network uptime, sensor latency, prospective deployment success, a site-population confidence interval, comfort or energy savings. No new prediction errors, p-values, or model tuning.

Post-result extension: after inspecting the initial availability totals, count a hypothetical issue-time fallback that uses the selector when ready, otherwise persistence when the current bin is available, otherwise the daily reference when its prior aligned bin is available, otherwise abstains. This readiness depends only on historical/current availability; compute target evaluability separately. The policy is a logical availability count only: no fallback forecasts, error or control outcomes are computed here, and it is not a prespecified primary analysis or evidence of useful deployment performance.
